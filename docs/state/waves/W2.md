## Risks for the integrator
- Edge against the real service: after the merge, run the web image with `API_UPSTREAM` pointing at the real service and check a calculation, a service problem passing through unchanged, the draining readiness 503 passing through, single-valued security headers on proxied API responses (service RF-API-08 copies hidden), the same `X-Request-ID` in the header, the problem body and the service log, and an invalid inbound ID replaced before it reaches the service.
- Request ID: the nginx `map` and `httpx.validRequestID` must accept the same set; test a 128- and a 129-character ID and a forbidden character through the edge.
- Problem codes: `httpx.Codes()` ⊆ contract enum = `PROBLEM_CODES`; the model's error copy covers all 13 codes; the edge emits only `RATE_LIMITED`, `SERVICE_UNAVAILABLE`, `PAYLOAD_TOO_LARGE`, each validating against `Problem`.
- Backend whole-module checks on the merged tree: `go vet ./...`, golangci-lint 0 issues, `go test -race ./...`, `-coverpkg=./internal/...` total ≥ 90 %; `go build ./...` without the `embedui` tag (only `noembed.go` exists until W3).
- Benchmarks (U12): the six `BenchmarkCalculate` cases < 1 ms and the worst-case cases < 50 ms, re-measured alone under the `heavy` lease; the margin of `power_fractional` was under 2× at W1 integration («Findings of W1» (c)).
- Frontend: `t0.sh`/`t2.sh` frontend stage covers the new model directory (typecheck, lint, format, tests) and coverage thresholds 90/90/90/85 still pass with the model included.
