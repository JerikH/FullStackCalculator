## Shape every ADR follows (rules)

```
# ADR-000N: <Title — exactly as in spec decision 6>

- **Status:** Accepted
- **Date:** 2026-10-22

## Context
## Decision
## Consequences
### Positive
### Negative
## Alternatives considered
```

- R1 — No other front-matter lines (no author, no deciders). Sections in exactly this order; nothing before `## Context` except the title and the two list lines.
- R2 — **Context** states the concrete forces (requirements with their RF/RNF IDs and numbers from `srs.md`), not generic motivation. **Decision** opens with one or two sentences stating the choice, then the specifics. Positive/Negative are bullet lists (≥ 2 bullets each, Negative includes what must now be maintained). **Alternatives considered** is a bullet list `- **<Alternative>** — <why it lost>` with every alternative named for that ADR below (≥ 2), each with a concrete reason tied to this system.
- R3 — Every number, string, ID, path, library and header name is copied from `srs.md` (or the committed contract). Nothing measured is claimed (no benchmark, coverage or size results); targets are stated as requirements («must stay under 1 ms/op, RNF-PERF-01»).
- R4 — Links: relative Markdown links only to these committed files: `../../backend/api/openapi.yaml`, `../../backend/api/spec.go`, `../../redocly.yaml`, `../spec/srs.md`, `../../.github/workflows/ci.yml.disabled` is NOT linked (write «the CI `contract` job»), and sibling ADRs (`0002-decimal-arithmetic-and-string-numbers.md`, …). Every other path (packages, Dockerfiles, `compose.yaml`, `Makefile`, nginx config, frontend files) is a plain code span, never a link. No heading anchors.
- R5 — Self-contained wording: never cite a document outside the repository, a task ID (only RF/RNF/UC IDs), a plan step number, a test-tier name, a section sign `§`, a time limit or the context the project was written in, and never use words suggesting reduced scope (deferred, skipped, postponed, descoped, not yet, for now, later version, TODO, TBD). Version 1 has exactly two topologies (the split `compose.yaml` stack and the all-in-one image); describe only those, and name no orchestration platform, monitoring server, dashboard or alerting product — not even as a rejected alternative (write generic classes: «a process supervisor», «distributed tracing», «a web framework»; the technologies a decision explicitly compares, such as binary floats or GraphQL, are fine). Metrics are «Prometheus text format» served by the service on its admin listener; who scrapes them is the operator's choice. CI is described as defined (its jobs and checks), never as running or publishing anything.
- R6 — English, plain and direct; 60–120 lines per ADR; cite the RF/RNF IDs inline (e.g. «(RF-CALC-02)»); link `../spec/srs.md` once near the top of Context.
- R7 — Cross-references between ADRs use sibling links (e.g. 0004 refers to [ADR-0002](0002-decimal-arithmetic-and-string-numbers.md) for the operand rules).

## Fact sheets (the content each ADR must carry)

### 0001 — Monorepo with independently deployable services
- Forces: a React + TypeScript web app and a Go REST service (srs 1.1) that share one contract (RF-API-01) and must be deployable and scalable separately (RF-OPS-04, RF-OPS-05, RF-OPS-06), plus a single-container delivery (RF-OPS-07); reviewers evaluate one repository (Reviewer actor, srs 2.2).
- Decision: one Git repository with `backend/` (Go module `github.com/JerikH/FullStackCalculator/backend`), `frontend/` (pnpm package `calculator-web`), `deploy/`, `scripts/`, `docs/`; three images built from the repository root as context (RF-OPS-01): `calculator-api`, `calculator-web`, `calculator` (srs 2.4); the root `Makefile` is the single entrypoint (RF-OPS-08); the contract lives with its provider in `backend/api/openapi.yaml` and the frontend's generated types `frontend/src/shared/api/schema.gen.ts` are committed (RF-API-10), so a contract change, its handlers and the regenerated types land in one commit; the API is versioned in the path (`/api/v1`); per-area CI jobs (`contract`, `backend`, `frontend`, `e2e`, `images`, `publish`, RF-OPS-11) and Dependabot entries per directory (RF-OPS-13).
- Positive: atomic cross-layer changes reviewed together; drift caught in one pipeline (RF-API-09, RF-API-10); one clone, one set of commands for reviewers and developers; independent images keep runtime independence.
- Negative: CI and repository tooling cover two ecosystems (Go and Node toolchains, two lockfiles `go.sum`/`pnpm-lock.yaml`, RNF-OPS-01); the pipeline is coupled — every change runs every job unless filtered; independent deployment depends on discipline: the web image and API image may be released at different times, so the contract must stay backward compatible within `/api/v1`; repository-root build context needs a strict `.dockerignore` (RF-OPS-01).
- Alternatives: **Separate repositories** (contract must be published and versioned as a package or copied; a contract change needs coordinated pull requests across repos; version skew between generated types and handlers is invisible to each repo's CI). **One inseparable server-rendered application** (Go templates or a single process serving HTML; the UI could no longer be deployed, cached and scaled independently of the API, the edge concerns of the split topology have no home, and the React + TypeScript single-page app of srs 1.1 would be dropped).

### 0002 — Decimal arithmetic and decimal strings on the wire
- Forces: a calculator must give `0.1 + 0.2 = 0.3` (RF-CALC-05); operands and results must survive JavaScript, whose `Number` is a binary double (≈15–17 significant digits; integers exact only to 2^53); every outcome must be classified (RF-CALC-09) and rounding must be visible to the user (RF-UI-06 `≈`).
- Decision: `cockroachdb/apd/v3` arbitrary-precision decimals with a fixed context — precision 34, half-even, adjusted exponents in [−6143, 6144] (decimal128-like), the trapped and untrapped conditions of RF-CALC-02. Every number on the wire is a JSON string in JSON-number syntax (regex of srs 1.3), ≤ 128 characters, ≤ 34 significant digits, exponent range checked, all invalid operands reported with their index (RF-CALC-03). Results formatted canonically mirroring JavaScript `Number#toString` (RF-CALC-04). `inexact: true` exactly when rounded (RF-CALC-09). Operands are echoed unchanged (RF-API-03). The frontend treats numbers as text only (RF-UI-03, RF-UI-05, RF-UI-06).
- Positive: exact decimal results where representable; 34 digits of precision end to end, no silent corruption in the browser; GDA conditions map directly to API errors (DivisionByZero → `DIVISION_BY_ZERO`, Overflow → `OVERFLOW`, InvalidOperation → `UNDEFINED_RESULT`; RF-CALC-05…07); cost per operation bounded by the precision cap, so no per-request timeout is needed (RNF-PERF-01: every `BenchmarkCalculate` case must run under 1,000,000 ns/op).
- Negative: explicit parsing and validation code with its own messages and limits (RF-CALC-03); JSON number tokens are rejected — `["0.1"]` is valid, `[0.1]` is a validation error (RF-API-04 rule 6), which is unusual for API clients; a third-party numeric library on the critical path whose formatting and condition flags must be pinned by tests (and fuzzing, RF-OPS-14); the frontend cannot use `Number`/`Intl.NumberFormat` and implements string-only grouping and sign display (RF-UI-06); results beyond 34 digits are rounded (`1 ÷ 3` → `0.3333333333333333333333333333333333`, inexact).
- Alternatives: **IEEE-754 binary floats** (`0.1 + 0.2 = 0.30000000000000004`; rounding is silent, no inexact signal; NaN/±Inf need special cases; JSON numbers parsed by JavaScript lose digits beyond double precision). **Integer fixed-scale** (a fixed number of decimal places cannot cover both `1e-7` and `1e+21`; int64 overflows; division, power and square root need rounding rules anyway). **Unbounded precision** (`1/3` and `√2` never terminate, so a cap is needed regardless; time and memory per request become unbounded, which would require per-request timeouts and larger abuse limits). Also mention, in the Decision or as a fourth bullet, **JSON numbers on the wire** (lose precision in JavaScript before the app sees them).

### 0003 — Provider-owned OpenAPI contract
- Forces: two consumers (the web app and direct API clients, srs 2.2) and one provider; the spec requires the service's responses and the frontend's types to never drift (RNF-REL-01).
- Decision: OpenAPI 3.1 document [`backend/api/openapi.yaml`](../../backend/api/openapi.yaml) owned by the Go service, components `Decimal`, `OperationName`, `CalculationRequest`, `CalculationResult`, `OperationInfo`, `OperationCatalog`, `ProblemCode`, `Problem`, `FieldViolation`, `Health`; linted with Redocly per [`redocly.yaml`](../../redocly.yaml) (`recommended` + `operation-4xx-response`, `no-unused-components`, `info-license-strict` as errors); embedded in the binary by [`backend/api/spec.go`](../../backend/api/spec.go) (`api.Spec`) and served at `GET /api/v1/openapi.yaml` as `application/yaml` with `Cache-Control: no-store` (RF-API-01). Drift gates: Go contract tests validate every handler response against the embedded document with `pb33f/libopenapi-validator`, assert the catalog equals the `OperationName` enum in order and the service's problem codes are a subset of `ProblemCode` (RF-API-09); TypeScript types generated with `openapi-typescript` into `frontend/src/shared/api/schema.gen.ts`, committed, regeneration must produce no diff (RF-API-10), checked by the CI `contract` job (RF-OPS-11); the client is `openapi-fetch` typed from the schema, and at runtime a non-2xx body is accepted as a problem only if it passes the `isProblem` guard (RF-UI-09). A contract change regenerates the types in the same change.
- Positive: one reviewable source of truth before code; compile-time checking of requests/responses in the frontend; runtime validation of real handler output in tests; the published document is the exact one the binary embeds; adding an operation is one catalog entry plus the enum, and the contract test fails on divergence.
- Negative: the YAML and the Go handlers are two representations kept in step by tests rather than by construction; tooling to maintain (Redocly, `openapi-typescript`, the validator) and generated code in the repository; a wrong-method 405 has no operation in the document, so contract tests validate its body against the `Problem` schema and assert `Allow` separately; runtime guards are still needed because types are erased at runtime.
- Alternatives: **Handwritten, duplicated types** (TS and Go types drift silently; nothing fails when a field is renamed). **Code-first contract generated from Go** (the contract becomes a side effect of refactors; consumers cannot review the shape before implementation; generator support for OpenAPI 3.1 and for problem+json responses is weaker than writing the document). **GraphQL** (a single POST endpoint returning 200 with errors in the body conflicts with the HTTP status semantics of [ADR-0004](0004-problem-details-and-status-semantics.md); a schema runtime and client for three resources is disproportionate; HTTP caching and per-route metrics become harder).

### 0004 — Problem details and status semantics
- Forces: three kinds of clients must react to errors programmatically (web app, curl users, edge); the UI shows fixed copy per error (RF-UI-08); errors must never leak internals or reflect raw input (RF-API-11, RNF-SEC-02); support needs to correlate a user report with logs (RF-API-07).
- Decision: every error response of the service (API routes and unmatched routes) is an RFC 9457 `application/problem+json` body `{type, title, status, detail, instance, code, requestId[, errors]}`, `type = urn:calculator:problem:<kebab-code>`, `instance` = request path, `errors[]` (field + reason) only for `VALIDATION_FAILED` (RF-API-05). Thirteen stable codes (table of RF-API-05, with status and title). Status semantics: 400 = the request is wrong (`MALFORMED_REQUEST`, `VALIDATION_FAILED`); 422 = well-formed but the mathematics has no representable answer (`DIVISION_BY_ZERO`, `UNDEFINED_RESULT`, `OVERFLOW`); 404 `UNKNOWN_OPERATION` checked before the body is read and 404 `NOT_FOUND` for unmatched routes; 405 with `Allow` (RF-API-06); 413/415 from the decoding order (RF-API-04); 500 `INTERNAL_ERROR` opaque (`an unexpected error occurred`) and logged with `request_id` and stack (RF-API-11); 429 `RATE_LIMITED` and 503 `SERVICE_UNAVAILABLE` are emitted only by the edge, which also emits 413 above its 1 MiB transport limit, with the same fields except that `instance` may be omitted (RF-OPS-04). `requestId` equals the `X-Request-ID` response header (RF-API-07). Mapping is centralized: domain sentinel errors (texts = API reasons, RF-CALC-03…09) map to problems in one place in the HTTP layer; the problem catalog is part of the shared HTTP plumbing. The draining readiness 503 is Health JSON (RF-OBS-03), not a Problem. Reflection exceptions are only the `%q`-quoted operation name, the quoted unknown field name and the 405 method (RNF-SEC-02).
- Positive: one shape for every failure, machine-readable `code` independent of wording; the UI maps codes to its own copy and never displays server `detail` or `title` (RF-UI-08); `Ref: <requestId>` ties a screen to a log line; the 400/422 split tells the client whether to fix the request or accept that the operation has no answer; validation reports every bad operand at once.
- Negative: the code list exists in three places (contract `ProblemCode` enum, the service's list, the frontend's list) and must be kept identical by tests (RF-API-09); exact detail strings are normative and asserted by tests, so changing copy is a contract change; 422 is less familiar than 400 to some clients; the edge must build the same JSON shape in its configuration; a 405 from the router cannot be validated as a documented response (see [ADR-0003](0003-provider-owned-openapi-contract.md)).
- Alternatives: **Ad hoc error strings** (clients parse prose; wording changes break them; no request correlation). **HTTP 200 carrying a failure in the body** (breaks HTTP semantics, caches, proxies, access-log status and metrics by status; every client must inspect every body). **One generic 400 for every failure** (the client cannot tell a malformed request from a division by zero, and the UI copy of RF-UI-08 depends on that distinction).

### 0005 — Standard-library HTTP and consumer-defined interfaces
- Forces: five public endpoints (RF-API-01…03, RF-OBS-02/03) and a private admin listener; strict and ordered decoding (RF-API-04); every error must be problem+json including 404/405 (RF-API-06); a fixed middleware order (RF-API-12); a domain that must be testable without HTTP; RNF-QUAL-02 lint rules.
- Decision: `net/http` with the standard `ServeMux` patterns (wildcards such as `{operation}`); no web framework. Packages and dependency rule: `backend/cmd/calculator` → `internal/app` (composition root, lifecycle) → `internal/httpapi` (routes, handlers, domain-error → problem mapping, health) → `internal/calc` (pure domain); `internal/platform/httpx` is generic HTTP plumbing with no calculator vocabulary except the API-wide problem catalog (problem+json, strict JSON decoding, request context and request ID, middleware, a `Methods` dispatcher that answers 405 with `Allow` as a problem); `internal/observability`, `internal/config` (stdlib, env only, RF-OBS-01), `internal/buildinfo`, `internal/web`. `internal/calc` imports no internal package and knows nothing about HTTP or JSON. Interfaces are defined by their consumers: `httpapi` and `observability` each declare the small `Calculator` interface they need, satisfied by `*calc.Calculator` and by the metrics decorator. Middleware chain outermost first RequestContext → AccessLog → Metrics → Recover → SecureHeaders → router (RF-API-12); routes are tagged with their pattern so logs and metrics never use raw paths (RF-OBS-05/06).
- Positive: no framework dependency to track (only stdlib on the request path besides `apd` and the metrics client); full control over the problem shape for 404/405/413/415; the domain is unit-tested and fuzzed without servers (RF-OPS-14); decorators (metrics) slot in without the domain knowing; small interfaces make test doubles trivial.
- Negative: plumbing a framework would supply is written and tested here (middleware chaining, 405 handling, strict decoding, response helpers, panic recovery); the method-dispatch helper exists because the standard mux answers wrong methods with a plain-text 405 instead of a problem; newcomers do not get framework conventions; each consumer interface duplicates a method signature.
- Alternatives: **A web framework** (an extra dependency and its own context and error conventions; its default 404/405/validation responses would have to be overridden to emit problem+json anyway; the standard mux already supports method and wildcard patterns). **Provider-owned broad interfaces** (an interface exported by `calc` with every method forces consumers to depend on methods they do not use and makes fakes larger; Go interfaces are satisfied implicitly, so the consumer can own them). **Layers without meaningful boundaries** (controller/service/repository layers for a service without a database add ceremony without isolating anything; the boundaries kept are the ones with distinct reasons to change: domain, transport, plumbing, runtime).

### 0006 — Server-authoritative arithmetic and a pure reducer
- Forces: results must be exact to 34 digits (see [ADR-0002](0002-decimal-arithmetic-and-string-numbers.md)) and the frontend must never compute one (RF-UI-05: no `Number`, `parseFloat`, `parseInt`, `BigInt`, `Intl.NumberFormat` on converted numbers, `eval` or a decimal library on operands or results); calculator input is a state machine with chaining, errors, a busy period and late responses (RF-UI-04); keypad and keyboard must behave identically (RF-UI-01, RF-UI-02).
- Decision: every numeric result comes from `POST /api/v1/operations/{operation}`; the frontend's only local logic is text editing of the entry (digits, decimal point, sign, backspace; RF-UI-03). The calculator is a pure reducer state machine (`entry`, `entryMode`, `accumulator`, `pendingOperator`, `inexact`, `status`, `error`, `request`, `history`, `nextRequestId`) with sequential chaining (`2 + 3 × 4 =` → 20; `5 + =` → 10; `2 + × 3 =` → 6). Effects live in a hook (`useCalculator`): one request per issued operation with an `AbortController`; AC drops and aborts it; completions whose request ID is not the current one are ignored, including after AC restarts request IDs; while busy only AC, success and failure are processed (RF-UI-04). The API client never throws, times out after 8 s and returns a typed outcome (RF-UI-09). Busy feedback: the value dims immediately, `aria-busy`, spinner only after 150 ms (RF-UI-07). One `KEYPAD` table drives keypad and keyboard (RF-UI-01). Feature layout: `frontend/src/features/calculator/model/` (pure: no React, no IO), `hooks/` (effects), `ui/` (presentational). State stays in `useReducer`; no global state library.
- Positive: one arithmetic implementation, so web and API clients always agree; the reducer is tested exhaustively without a DOM (every transition and guard); stale or cancelled responses can never change the display or history (RNF-REL-01); keypad/keyboard parity by construction; strings end to end.
- Negative: one network round trip per operation (latency, mitigated by same-origin keep-alive and the 150 ms spinner delay); no calculation without the service — offline or unreachable shows `Calculator service is unreachable` (RF-UI-08); input during a pending request is ignored rather than queued; an explicit state machine is more code than ad hoc handlers and must be kept in step with its transition tests.
- Alternatives: **Client-side arithmetic or optimistic results** (JavaScript numbers are imprecise; a second implementation would diverge from the service; an optimistic value later corrected by the server is worse than a short wait). **A global state library** (Redux, Zustand: a dependency and indirection for one component tree whose state fits `useReducer`; the pure reducer is already framework-free and testable). **Logic spread over component handlers** (rules hidden in event handlers need a DOM to test; races between clicks and responses are hard to reason about; keypad and keyboard would duplicate logic).

### 0007 — Split and embedded delivery
- Forces: the web app and the API must be deployable and scalable independently (RF-OPS-04…06), and the whole product must also run from one container with one command (RF-OPS-07); every topology is same-origin, so no CORS is needed (srs 1.2); browser security policy (RNF-SEC-03), caching and rate limiting need an owner; containers are hardened (RNF-SEC-04).
- Decision: two topologies from one codebase. **Split** (`compose.yaml`, services `api` and `web`, RF-OPS-06): `calculator-web` (nginx-unprivileged alpine, port 8080, non-root) serves the built app (`index.html`, `/theme-init.js` and static files `no-cache`; hashed `/assets/*` `public, max-age=31536000, immutable`), proxies `/api/*`, `/healthz`, `/readyz` unchanged to `API_UPSTREAM` (default `api:8081`), answers `/nginx-health`, never routes metrics or pprof, owns the browser policy (one value per header, upstream copies hidden), gzips text, rate-limits API locations at 20 r/s burst 40 per client address, propagates a validated `X-Request-ID`, and emits the edge problems 429/503/413 (RF-OPS-04); `calculator-api` (distroless static nonroot, `:8081` and `:9091`, healthcheck `["/calculator","healthcheck"]`, RF-OPS-05). Only web is published (`8080:8080`); healthchecks gate startup; `read_only`, `cap_drop: [ALL]`, `no-new-privileges`. **Embedded** (root `Dockerfile` → `calculator`, RF-OPS-07): one Go binary built with `-tags embedui` embeds the built app (`internal/web`), listens on `:8080` (`CALC_HTTP_ADDR=:8080`) and serves the same app, API, browser policy and cache headers from one port; without the tag the binary serves the API only. Header ownership: the service sets its own headers when reached directly; behind the edge the edge owns them (RF-API-08).
- Positive: the split topology shows the production shape — independent images, edge concerns (rate limit, compression, caching, browser policy) outside the application, the admin port never published; the embedded image gives a one-command demo (`docker run -p 8080:8080 calculator:local`) that also runs read-only with all capabilities dropped; same-origin everywhere means no CORS surface; the same frontend build and the same API code run in both.
- Negative: two delivery paths to build, test and document (compose E2E, RF-OPS-10, and `scripts/smoke-aio.sh` for the all-in-one image); the browser policy and cache rules exist twice (nginx configuration and the Go web handler) and both must be asserted; the embedded topology has no edge rate limiting or compression — rate limits are per edge instance (srs 1.2: distributed rate limiting is a design exclusion), so an all-in-one deployment needs an external edge for equivalent controls; the build-tag split means the embed path must be exercised explicitly.
- Alternatives: **Only split** (no single-container delivery; trying the product requires Compose and two images). **Only embedded** (web and API could not be released or scaled independently; rate limiting, compression and edge problems would move into the Go service). **Multiple supervised processes in one container** (nginx plus the Go binary under a process supervisor: an init system, two processes' signals, logs and health in one container, a larger image, and one process per container lost).

### 0008 — Observability and drain-aware readiness
- Forces: operators need to correlate an edge or UI error with a service log line (RF-API-07, RF-UI-08 `Ref`), see rates, latency and outcomes (RF-OBS-06), and restart or roll the service without dropping in-flight requests (RF-OBS-03/04); metrics and profiling must not be public (RF-OBS-07, RNF-SEC-04); labels must never carry client input (RNF-SEC-02).
- Decision: structured logs with `log/slog` (JSON by default, text optional; `CALC_LOG_LEVEL`, `CALC_LOG_FORMAT`, RF-OBS-01); every context-aware line carries `request_id`; one access-log line per request at `info` (`error` for 5xx) with `method`, `route` (matched pattern, never the raw path), `path`, `status`, `bytes`, `duration_ms`, `remote_addr`, `user_agent` (RF-OBS-05). Request IDs: an inbound `X-Request-ID` matching `^[A-Za-z0-9._-]{1,128}$` is propagated, otherwise generated with `crypto/rand.Text()`; every response carries it and a problem's `requestId` equals it (RF-API-07); the edge propagates a validated value (RF-OPS-04). Metrics in Prometheus text format from a custom registry on the private admin listener (`CALC_ADMIN_ADDR`, default `:9091`, empty disables it): `http_requests_total{method,route,status}`, `http_request_duration_seconds{method,route}` (buckets .0005 … 1), `http_requests_in_flight`, `calculator_operations_total{operation,outcome}`, `calculator_build_info{version,commit,go_version}`, plus Go and process collectors; bounded labels (unknown methods → `OTHER`, unknown operations → `unknown`, routes are patterns; outcomes from the fixed set of RF-CALC-10) (RF-OBS-06). `pprof` only when `CALC_PPROF=true`, only on the admin listener (RF-OBS-07). Version and commit via ldflags with VCS fallback (RF-OBS-09). Probes: `/healthz` liveness never depends on downstreams (RF-OBS-02); `/readyz` 200 ready / 503 draining (RF-OBS-03) — the draining 503 is Health JSON (`{"status":"draining",…}`), not a Problem (RF-API-05), and the edge passes it through unchanged (RF-OPS-04). Lifecycle: on SIGINT/SIGTERM readiness flips to draining, the service waits `CALC_SHUTDOWN_DRAIN` (default `0s`; the compose stack sets `2s`, RF-OPS-06), then shuts both listeners down within `CALC_SHUTDOWN_TIMEOUT` (default `15s`); server timeouts ReadHeader 5 s, Read 10 s, Write 15 s, Idle 60 s, MaxHeaderBytes 16 KiB (RF-OBS-04). `calculator healthcheck` probes `/healthz` with a 2 s timeout because distroless images have no curl (RF-OBS-08).
- Positive: a single ID follows a request from the browser through the edge to the service log; whoever scrapes the admin listener gets rates, latency, in-flight requests and operation outcomes without code changes; bounded label sets keep the metrics cheap and free of client data; a proxy or load balancer polling `/readyz` stops routing before shutdown, so in-flight requests finish; liveness stays green during drain, so a draining instance is not restarted.
- Negative: observability has a maintenance cost — metric names, labels and buckets are an interface that tests must pin and changes must keep compatible; a second listener to configure and keep unpublished; drain lengthens every shutdown by `CALC_SHUTDOWN_DRAIN`, and the container stop grace period must cover drain plus shutdown (RF-OPS-06); logs, not traces, are the correlation tool.
- Alternatives: **Public metrics on the main listener** (exposes internals to any visitor, mixes operational and product routes, and the edge would need exclusion rules; the admin listener is never routed or published). **Raw-path labels** (unbounded cardinality from arbitrary URLs and client input in label values, violating RNF-SEC-02). **Liveness tied to readiness** (a draining or briefly unready instance would be killed and restarted, cutting the in-flight requests the drain exists to protect). **Distributed tracing without a current need** (one service with no downstreams; the request ID already correlates edge and service logs; an SDK and collector would add dependencies and configuration for no new information).
