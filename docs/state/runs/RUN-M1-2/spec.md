## Design decisions

D1 — **Dependency versions (U10 under declared constraints).** Each dependency at its latest stable release whose declared peer ranges and Node engine range are satisfied by the rest of the set on the pinned runtime (Node 24.14.1 locally and in CI). Four packages cannot take their absolute latest:
- `typescript` 5.9.3: `typescript-eslint` 8.72.0 declares `typescript >=4.8.4 <6.1.0` and `openapi-typescript` 7.13.0 declares `^5.x`; 5.9.3 is the newest release satisfying both (6.0.3 breaks the second, 7.0.2 both).
- `eslint` 10.13.0 and `@eslint/js` 10.0.1 are kept at their latest even though `eslint-plugin-jsx-a11y` 6.10.2 (latest, required by RNF-QUAL-02) declares `eslint ^3 … ^9`: the newest 9.x (9.39.5) is marked deprecated on the registry («This version is no longer supported»), and the plugin's `lib/` uses none of the rule-context methods ESLint 10 removed (grep for `getSourceCode`, `getScope`, `getFilename`: no match). The peer range is widened with `pnpm.peerDependencyRules.allowedVersions` (`eslint-plugin-jsx-a11y>eslint: 10`), and a lint fixture proves the plugin's rules fire under ESLint 10 (an `<img>` without `alt` fails `jsx-a11y/alt-text`).
- `jsdom` 29.1.1: jsdom 30.x declares `node ^22.22.2 || ^24.15.0 || >=26`, above the Node 24.14.1 pinned locally and in the CI `contract` job; moving the pin is outside this run (machine-wide toolchain, the workflow's Node pin belongs to OPS-CI-02's version source). Recorded as a finding so the bump happens with the Node pin.
- `@types/node` 24.19.2 (latest 26.6.5 is not excluded by any declared range): the definitions follow the runtime major, so code calling an API Node 24 lacks fails the typecheck instead of failing at run time; the Vite 8 template makes the same choice. Recorded as a finding with the jsdom one; the owner may prefer the absolute latest.
Everything else at its latest (vite 8.3.5, react/react-dom 19.3.1, @vitejs/plugin-react 6.1.2, openapi-fetch 0.17.0, openapi-typescript 7.13.0, @redocly/cli 2.69.0, vitest/@vitest/coverage-v8 5.0.5, msw 3.0.3, @testing-library/react 16.3.3, user-event 14.6.8, jest-dom 7.0.1, dom 10.4.2, vitest-axe 0.1.0, @playwright/test 1.64.1, @axe-core/playwright 4.14.0, @types/react(-dom) 19.3.0, typescript-eslint 8.72.0, eslint-plugin-react-hooks 7.1.1, eslint-plugin-react-refresh 0.5.7, eslint-config-prettier 10.1.8, globals 17.13.0, prettier 3.9.10). D10 — **API client** (RF-UI-09, F5). Types, `problem.ts`, `calculatorApi.ts`, context and provider per plan.md, with these decisions:
- `isProblem` checks every required field of the generated `Problem` (`type`, `title`, `detail`, `requestId` strings; `status` an integer 400–599; `code` ∈ `PROBLEM_CODES`) and, when present, `instance` (string) and `errors` (array of `{field: string, reason: string}`), so `value is Problem` is sound. The problem result copies `detail` and `requestId` unconditionally (F5); `ApiError` keeps them optional.
- A problem body whose `status` differs from the HTTP status is not trusted: `unexpected(<HTTP status>)`. Otherwise `problem.status` is that common value.
- An empty `requestId` passes the guard (the contract only says string); the copy rule «`Ref: <requestId>` when available» is the model's (UI-MODEL-01), recorded as a hand-off finding.
- Success bodies are guarded too: a 2xx is `ok` only when the body is a `CalculationResult` for the requested operation (`operation` equal to the requested one, `operands` an array of strings, `result` a string, `inexact` a boolean); anything else (including an empty or 204 body) → `unexpected(status)`. Without this, a 2xx with a body the UI cannot show would reach the display as `ok`.
- Failure classification: the per-request `fetch` records the response status. In the `catch`: when the combined signal is aborted, its `reason` tells which source fired first (`AbortSignal.any` keeps the first source's reason): the timeout's reason → `timeout`, anything else → `aborted`; else a response was received and the error is named `SyntaxError` (`error instanceof Error && error.name === 'SyntaxError'`, realm-independent; an unparsable 2xx body) → `unexpected(status)`; else → `network`. A timeout that fires while the body is still arriving is a `timeout`.
- Base URL (RF-UI-09): `resolveBaseUrl(configured: string | undefined, origin: string): string` returns `configured` when it is a non-empty string, else `origin` (an empty `VITE_API_BASE_URL` falls back to the page origin). The single `createCalculatorApi({ baseUrl: resolveBaseUrl(import.meta.env.VITE_API_BASE_URL, window.location.origin) })` call and the provider around the app belong to the real `main.tsx` of UI-SCREEN-01; this run provides and tests both pieces.
- `PROBLEM_CODES` keeps the compile-time two-way check (`satisfies readonly ProblemCode[]` against extra codes, an `Exclude` against missing ones).
- `createCalculatorApi` copies `operands` (`[...operands]`) into the body and never mutates caller data.
- `useCalculatorApi` outside the provider throws a programming error (it is not an API call; the never-throw rule covers `calculate`).
