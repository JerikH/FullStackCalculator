### Findings of OPS-EDGE-01 — web image and nginx edge (2026-10-22)
- (a) **OPS** [topic: edge-proxy, security-privacy, rate-limit] [type: rule] — Rule as built: `frontend/Dockerfile` builds the app in `node:24.14.1-alpine3.23` (tag + index digest, `--platform=$BUILDPLATFORM`, pnpm 10.33.0 through corepack from `packageManager`, `pnpm install --frozen-lockfile` with a BuildKit store cache, `pnpm run build`, then asserts `index.html`, `theme-init.js`, `assets/*.js` and their `.map`) and serves it from `nginxinc/nginx-unprivileged:1.30.6-alpine3.24` (tag + index digest) as uid 101 on `:8080`, docroot `/usr/share/nginx/calculator` (base `/usr/share/nginx/html` and `conf.d/default.conf` removed, `conf.d` mode 1777 so a plain tmpfs renders the template), template `/etc/nginx/templates/default.conf.template`, snippets `/etc/nginx/snippets/{security-headers,proxy-api}.conf`, `API_UPSTREAM=api:8081`, `NGINX_ENVSUBST_FILTER=^API_UPSTREAM$`, healthcheck `wget -q --spider -T 2 http://127.0.0.1:8080/nginx-health` (10 s/3 s/5 s/3). Routes: `= /` index, `/` static `try_files $uri =404` with `no-cache` on hits, `/assets/` `public, max-age=31536000, immutable` on hits only (`.map` as `application/json`), `= /nginx-health` 200 `ok`, `= /api` 404, `/healthz` and `/readyz` proxied directly with the routed path and no body (no limit, no interception; only an unreachable service becomes the 503 problem; above 1 MiB the 413 problem), everything else static 404. `/api/` uses two hops in one nginx: the outer location applies `limit_req zone=api burst=40 nodelay` (20 r/s per `$binary_remote_addr`, status 429), the 1 MiB `client_max_body_size` and the edge 413/429 pages without `proxy_intercept_errors`, and proxies the routed (normalised) path, never the raw target, to an inner server on `127.0.0.1:8079` (connect 2 s, send/read 15 s) that proxies to the service with `proxy_intercept_errors on` for 502/503/504 only — nginx intercepts every status that has an `error_page` in the proxying location, so one hop would replace the service's own 413 (evidence/intercept-collision.txt). Service hops: HTTP/1.1, `Connection: close`, connect 2 s, send/read 10 s, `proxy_next_upstream off`, `Host` = the client's (default `localhost`), `X-Request-ID` = `$correlation_id` (`map` of the contract pattern, otherwise `$request_id`). The edge owns the five RNF-SEC-03 headers and `X-Request-ID` (`add_header … always` at server level and in every location that adds headers; upstream copies hidden); `Cache-Control`, `Cross-Origin-Resource-Policy` and `Allow` pass through from the service. Edge problems are constant JSON plus `$correlation_id`, `types { }` + `application/problem+json`, `Cache-Control: no-store`; 413 detail `request body must not exceed 4096 bytes` (the catalog's detail for the code). gzip on for CSS, JS, JSON, problem+json, YAML, SVG and text above 1 KiB, `gzip_vary on`; `server_tokens off`; client header/body and send timeouts 10 s; `X-Accel-*` headers from the service ignored.
- (b) **API, OPS** [topic: api-contract, edge-proxy] [type: debt] [target: API-backlog] — The contract declares no 503 on `/healthz` and only a Health JSON 503 on `/readyz`, but behind the edge an unreachable or timed-out service makes both probes answer the edge's 503 `SERVICE_UNAVAILABLE` problem (`application/problem+json`; the draining readiness 503 still passes through unchanged). The alternative, nginx's HTML 502/504 page, matches the contract no better. Proposed fix (contract change, owner decision): add the `ServiceUnavailable` response to `/healthz` and an `application/problem+json` `Problem` alternative to the `/readyz` 503, both described as emitted by the edge proxy.
- (c) **OPS** [topic: edge-proxy, deployment-infra, reliability-errors] [type: debt] [target: OPS-STACK-01] — nginx resolves `API_UPSTREAM` when it starts: after the `api` container is recreated with a new address, `/api/*` and the probes answer the 503 problem until `web` restarts (reproduced by the spec reviewer: 172.25.0.2 → .5, `/nginx-health` stayed 200). Re-resolution in nginx would need the resolver address rendered into the template (a second substituted variable) and would stop resolving names from `/etc/hosts`. Fix in the compose stack: `web.depends_on.api: { condition: service_healthy, restart: true }`, and prove it by recreating `api` in the running stack (`docker compose up -d --force-recreate api`) and calling `/api/v1/operations` through `web`.
- (d) **UI, OPS** [topic: edge-proxy, ci-supply-chain] [type: note] — Source maps are named after their chunk (`assets/index-<hash>.js.map`), so a change that alters only the map's `sourcesContent` (for example a comment the minifier drops) could keep the name with new content while the edge serves it with the one-year immutable policy chosen in U14; the consequence is stale sources in developer tools, never stale code. Not reproduced (it needs two builds of differing sources); recorded so a future build change (content-hashed map names or `sourcemap: 'hidden'`) can take it into account.
- (e) **OPS** [topic: deployment-infra, testing-environment, edge-proxy] [type: trap] — Docker and nginx traps met here: a plain `--tmpfs <dir>` (and compose `tmpfs:`) mounted over an existing directory takes that directory's mode but is owned by root (nginx-unprivileged's `conf.d` became `root:root 775`); nginx-unprivileged's `20-envsubst-on-templates.sh` then logs `ERROR … not writable` and nginx still starts, with no server at all — only the healthcheck shows it. `return <code> '<text>'` takes the MIME type from the request URI's extension (`/api/x.js` → `application/javascript`) unless the location resets `types { }`. `proxy_intercept_errors on` intercepts every status that has an `error_page` in that location. nginx round-robin state is per worker (`worker_processes auto`): a few requests can all reach the first of two upstream addresses. A failed ARP lookup is cached, so only the first connect to an unused address waits for the connect timeout. `docker logs` is written asynchronously (wait before counting lines). `bash` reads a script while running it: do not edit a smoke script while a run of it is in progress.
- (f) **OPS** [topic: testing-environment] [type: note] — `scripts/ci/t0.sh` selects the frontend stage for any path under `frontend/`, `frontend/Dockerfile` included, and that stage needs `frontend/node_modules`; this worktree has none (W2: RUN-M1-6 installs nothing on the host), so the worker's t0 ran the shell and dockerfiles stages (shellcheck, hadolint: pass) and the frontend stage stopped at the install check. The TypeScript build (`tsc -b && vite build`) ran inside every image build. With the frontend installed (main checkout) the stage runs the typecheck and `prettier --check --ignore-unknown` on the Dockerfile.
- (g) **OPS** [topic: edge-proxy, live-verification] [type: verification] [target: OPS-E2E-01] — The edge was proven against a stub of the service (evidence/stub-upstream.mjs, which answers an oversize POST at the 4097th byte with `Connection: close`, half-closes and resets after 500 ms like `http.MaxBytesReader`). Against the real service, through the composed stack: a calculation, the service's own 413 for a 5000-byte and a 1 MiB body passing through unchanged, an application problem passing through, the draining readiness 503 passing through, single-valued security headers on proxied API responses, the same `X-Request-ID` in the header, the problem body and the service log, a 128-character ID kept and a 129-character or `<script>` ID replaced before it reaches the service, and the 429 problem under a burst.
- (h) **OPS** [topic: security-privacy, rate-limit, deployment-infra] [type: debt] [target: OPS-STACK-01] — Slow uploads held open fill the RAM-backed `/tmp`: `limit_req` limits how fast requests start, not how many are open, and every body above 16 KiB is buffered in `/tmp/client_temp` (security review: 40 held 1 MiB uploads = 39.8 MB; the ceiling is workers × 1024 connections × 1 MiB; the unlimited probes read and bound a body before discarding it, so they are the cheapest way to do it). The edge now drops a client that stops sending for 10 s (`client_body_timeout`). Remaining: the compose stack caps the web tmpfs (`/tmp` with a `size=` such as 64m; a full `/tmp` then fails new large bodies instead of the host's memory), and the owner decides whether the edge adds a per-address connection limit (`limit_conn_zone $binary_remote_addr`, e.g. 20 on `/api/` answered with the `RATE_LIMITED` problem), which RF-OPS-04 does not name today.
- (i) **OPS, DOC** [topic: rate-limit, deployment-infra] [type: debt] [target: DOC-README-01] — The rate limit keys on the client address nginx sees. Behind Docker's userland proxy (the default for published ports on 127.0.0.1, rootless Docker, Docker Desktop) every client arrives as the bridge gateway (security review: all requests logged as `172.24.0.1`), so all clients share one 20 r/s budget; forwarded-address headers are deliberately not trusted. The README's trade-offs state this for the local topology.
