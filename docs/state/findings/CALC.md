# Findings — CALC (Calculation engine)

### Findings of CALC-CORE-01 — Go module, lint configuration, decimal parsing and formatting (2026-10-22)
- (a) **CALC** [topic: numeric-precision] [type: rule] — Rule as built: `calc.Parse` (`backend/internal/calc/decimal.go`) applies RF-CALC-03 in order: length in characters (`utf8.RuneCountInString` > 128 → `must be at most 128 characters`), the decimal-string regex, then — from the validated text, before apd parses anything — a zero test (every coefficient digit `0` → a zero with exponent 0 keeping its sign, so `0e9999999999` is valid) and the significant-digit count (coefficient digits without leading and trailing zeros > 34 → `must have at most 34 significant digits`), then apd parsing (failure = exponent beyond int32 → range reason) and the adjusted-exponent range [−6143, 6144]; the returned decimal is reduced (same value, bounded cost). `calc.Format` renders zero and −0 as `0`, plain notation for adjusted exponents in [−6, 20], otherwise lowercase scientific with an explicit sign. `FuzzParse` pins the Format → Parse round trip and the wire syntax of every formatted value.
- (b) **CALC** [topic: numeric-precision, testing-environment] [type: trap] — apd v3.2.3 parses the exponent with `strconv.ParseInt(…, 32)` and fails before any digit check, so validation order cannot be delegated to `apd.NewFromString`: a 35-digit operand with an exponent like `e9999999999` must be counted from the text to get the digits reason, and a zero with such an exponent must be recognised from the text to be accepted. A zero kept with a huge stored exponent would also reach `Pow`/`Sqrt` as a clamped value; normalising it to exponent 0 removes that path.
- (c) **CALC, OPS** [topic: testing-environment] [type: note] — First real backend stage of `scripts/ci/t0.sh --base main` on this change: `golangci-lint fmt --diff`, `go vet`, `golangci-lint run` and `go test -race` over `./...` (full mode because `go.mod` is new) pass in 4.67 s; `ci_stage_backend` needed no change. The incremental path (touched packages and their dependents) ran on the API-HTTPX-01 commit alone (evidence/t0-incremental.txt). `go mod tidy` downloads `github.com/lib/pq` (a test dependency of apd) into the module cache; it is not a requirement of the module.

### Findings of CALC-OPS-01 — Operation catalog and calculator (2026-10-22)
- (a) **CALC** [topic: numeric-precision] [type: rule] — Rule as built: `Calculate` checks the context, the operation name, the arity, then every operand (all failures collected with their index); it applies the operation on a per-call copy of the decimal128-like context; pre-checks fix divisor zero, `0^0 = 1`, zero base with a negative exponent, negative non-zero base with a non-integer exponent and negative non-zero square roots; a failing `Pow` with an overflow/underflow condition is classified from the operands (|base| > 1 with a positive exponent or |base| < 1 with a negative one → OVERFLOW, otherwise 0 and inexact); `1^y = 1` exactly; an exact fractional power whose reduced exponent is p/q with q ≤ 64 and |p| ≤ 64 is verified exactly (`r^q = base^p`, or `r^q·base^|p| = 1`) by comparing the integer coefficients and exponents of the reduced values, and reported `inexact: false`; a non-finite result is OVERFLOW; a finite non-zero result below adjusted exponent −6143 becomes `0`, inexact, so every result is a valid operand.
- (b) **CALC** [topic: numeric-precision, testing-environment] [type: trap] — apd v3.2.3 behaviours the tests pin: `Pow` with a huge integer exponent fails with `exponent out of range` and unreliable flags (`0.1^-1e30`, which overflows, reports only Underflow; `0.1^1e30` reports only Underflow); exact fractional powers are flagged Inexact (`4^0.5`, `16^0.25`, `1^0.5`); exact square roots are never flagged Inexact (0 of 20,000 perfect squares), so the squaring check of RF-CALC-07 is defensive and its mutation is «the helper always answers exact» (then `sqrt 2` turns exact); subnormal results below the range are kept by apd (`1e-6143 ÷ 10 = 1e-6144`) unless flushed.
- (c) **CALC** [topic: performance-scale] [type: debt] [resolved: API-ROUTES-01] — The six `BenchmarkCalculate` cases of RNF-PERF-01 run in 2.1–302 µs (evidence/bench.txt), but fractional powers at the range edges cost far more: `(1.5e-6143)^-0.999…9` 13.2 ms, `(9.999…e6144)^0.999…9` 12.1 ms, `(9.999…e6144)^0.5` 6.7 ms, `(−1)^1e6144` 4.3 ms (evidence/power-worst-case.txt; apd's exp/ln path; up to 17.7 ms before operands were reduced). Still bounded by the operand limits, but it contradicts the «every operation well below 1 ms, so no per-request timeout» rationale. Options for the owner: accept and document the bound in the README performance numbers; add a worst-case benchmark case; or bound the working precision of fractional powers.
- (d) **CALC** [topic: numeric-precision] [type: note] — Residual of the exactness check: an exact fractional power whose exponent reduces to p/q with q > 64 or |p| > 64 (for example `1267650600228229401496703205376^0.01` = 2^100 raised to 1/100 is exactly `2`, but q = 100; `18446744073709551616^0.015625` = 2^64 raised to 1/64, q = 64, is verified exact) keeps apd's Inexact flag. Operands are limited to 34 digits, so such exact results are rare; the bound keeps the verification cost below the cost of the power itself.
- (e) **CALC** [topic: agent-process] [type: note] — Cycle notes: probes of apd before the plan found the underflow-classification defect (`0.1^1e30` would have been an `internal` error) and the over-reported inexact flag; the spec review found case-insensitive JSON keys, 413 after 400 with a streaming decoder, subnormal results outside the range, `−0` caught by the negative-base check and byte-counted length; the plan review found the digit check placed after the exponent parse. The diff review found `1^0.001` reported inexact and the untested non-finite guard; the security review found the verification context overflowing for large bases, the cost of unreduced operands and the swallowed panic after a started response. Nineteen mutation checks, each caught by a test (two first attempts did not compile and one survived; all three were redone with a compiling mutation or a new test row, evidence/mutations.txt).
