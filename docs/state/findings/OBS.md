# Findings — OBS (Service runtime and observability)

### Findings of OBS-METRICS-01 — Build info, request-aware logger and metrics (2026-10-22)
- (a) **OBS** [topic: observability, security-privacy] [type: rule] — Rule as built: `buildinfo.Get()` reports the ldflags `Version`/`Commit`, falling back to the first 12 characters of the embedded `vcs.revision` (else `unknown`); `observability.NewLogger` adds `request_id` from `httpx.RequestID(ctx)` to every record logged with a request context; `Metrics.Middleware` increments `http_requests_in_flight` and records `http_requests_total{method,route,status}` and `http_request_duration_seconds{method,route}` in a deferred call that never recovers, reading `httpx.Info(ctx).Route` and `StatusOrOK()` (`unmatched`/200 without request info), so a request that unwinds with `http.ErrAbortHandler` after `Recover` recorded 500 is counted as 500; methods outside GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONS are `OTHER`; `InstrumentCalculator` labels names outside the catalog snapshot `unknown` and outcomes with `calc.Outcome`. 120,000 requests with distinct methods, paths and operation names left the series count unchanged (security review).
- (b) **OBS** [topic: observability] [type: note] — The context handler adds `request_id` to the record, so on a logger that opened a `WithGroup` the attribute nests inside the group (`g.request_id`). The service never opens a group on a request-scoped logger, so every line it writes carries a top-level `request_id`; a future grouped logger must add the attribute itself or the handler must be extended.
- (c) **OBS** [topic: testing-environment, agent-process] [type: trap] — `go get <module>@<version>` adds the requirement but not the `go.sum` lines of packages that nothing imports yet; a subagent building the observability package then failed with «missing go.sum entry» for `prometheus/common`, `client_model`, `procfs`, `testutil`'s dependencies. Under the `deps` lease, `go get` the exact packages the run will import (`…/prometheus`, `…/prometheus/collectors`, `…/prometheus/promhttp`, `…/prometheus/testutil`, `libopenapi-validator/schema_validation`) before dispatching, and `go mod tidy` once at the end.

### Findings of OBS-RUNTIME-01 — Configuration, lifecycle, admin listener and entrypoint (2026-10-22)
- (a) **OBS** [topic: reliability-errors, observability] [type: rule] — Rule as built: `config.Load` reads the seven `CALC_*` variables (a set-but-empty value is a value: empty admin address disables the admin listener, empty HTTP address is invalid), requires host:port with a numeric port 0–65535, levels case-insensitive, timeout > 0, drain ≥ 0, `ParseBool`, and joins every failure as `NAME="value": reason`. `app.New` composes RequestContext → AccessLog → Metrics → Recover → SecureHeaders → router and binds both listeners, closing what it bound on a later failure. `Run` serves both, returns `server failed` on a serve error (also one during the drain), otherwise on cancellation flips readiness, logs `shutdown started`, waits the drain, shuts both servers down in parallel under one `CALC_SHUTDOWN_TIMEOUT` deadline, `Close()`s them past it, waits for every `Serve` goroutine and logs `shutdown complete`. `Main`: serve-mode configuration error → stderr, exit 2; unknown subcommand → 2; startup or run failure → 1; `healthcheck` exits 1 on any failure (configuration, extra argument, probe error, non-200, unreadable body) within the 2 s client timeout, probing loopback for wildcard hosts. `cmd/calculator` restores default signal handling after the first signal.
- (b) **OBS** [topic: reliability-errors] [type: note] — Past the shutdown deadline `Close()` closes every connection and cancels request contexts, and `Run` waits for the `Serve` goroutines, not for handlers: a handler that ignores its context keeps running until the process exits. Calculations are bounded (RNF-PERF-01), so no handler of this service can outlive the process meaningfully.
- (c) **OBS** [topic: observability] [type: debt] [resolved: OBS-LOG-01] — The draining `/readyz` 503 is logged at ERROR (RF-OBS-05: 5xx at error), so every deploy or rolling restart emits one ERROR line per readiness probe during the drain (seen in the smoke run). Options for the owner: keep (spec as written), or log the draining readiness 503 at INFO/WARN as an exception in RF-OBS-05.
- (d) **OBS** [topic: observability, security-privacy] [type: debt] [resolved: OBS-LOG-01] — The access log writes the full path and User-Agent (up to the 16 KiB header limit each) and the client `remote_addr` on every request (RF-OBS-05 fields): one client can add about 30 KB of log per request, and a direct client's IP is personal data (behind the edge it is the proxy's address). Options for the owner: truncate path and User-Agent (for example to 256 characters) in `httpx.AccessLog`, and record `remote_addr` as accepted or mask it.
- (e) **OBS, OPS** [topic: deployment-infra, security-privacy] [type: note] — The admin listener defaults to `:9091` on every interface (RF-OBS-01) and has no authentication; pprof is off unless `CALC_PPROF=true`. Exposure is controlled by deployment: the compose stack must not publish 9091 (RNF-SEC-04) and sets `CALC_SHUTDOWN_DRAIN=2s` so the draining 503 is visible to the edge before the listener closes (with the default `0s` it never is).
- (f) **OBS** [topic: agent-process, testing-environment] [type: trap] — The Codex sandbox could not bind sockets (`operation not permitted`) nor write Go's build cache in review mode, so Codex reported the lifecycle suite as unverified and added in-memory duplicates of the socket tests to exercise its mutations; the controller ran the real suite (97.9 %), removed the duplicates that only repeated socket tests (coverage unchanged) and kept the two that cover distinct branches. Lifecycle work dispatched to Codex is verified by the controller on real sockets.
- (g) **OBS** [topic: reliability-errors, testing-environment] [type: note] — Lifecycle tests are deterministic: an unexported `drainHook` blocks shutdown until the test has observed `/readyz` 503 and `/healthz` 200; the in-flight test wraps the public listener to learn that `Shutdown` closed it and asserts `Run` is still waiting before it releases the handler; every wait is bounded (5 s). `go test -race -count=20` over app, httpapi and observability passed (64 s), and a 32-client keep-alive load through a 3 s drain completed every request that reached a handler (3,965 logged = 3,965 counted by the clients; security review).

### Findings of OBS-LOG-01 — Access-log levels and field bounds (2026-10-22)
- (a) **OBS** [topic: observability, security-privacy, reliability-errors] [type: rule] — Rule as built (`httpx`, `httpapi`): `RequestInfo` carries an optional level (unexported `level`/`levelSet`) set through `httpx.SetAccessLevel(ctx, level)` (a no-op outside `RequestContext`); `logAccess` uses the handler's level when set, else `error` for 5xx and `info` otherwise, and never reads the path. The readiness handler sets `info` only on its draining 503, immediately before writing it. `Recover` clears any level on every panic, `http.ErrAbortHandler` included, before re-panicking or answering, so a handler that set `info` and then panicked or aborted is still logged at `error`. `path` (`r.URL.Path`, decoded) and `user_agent` are cut to their first 256 characters (runes) by `truncateChars`, which stops walking at the 257th rune and returns the string itself when it fits; a cut always falls on a rune boundary, an invalid byte counts as one character, nothing is appended. The bound is on characters: the raw field is at most 1024 bytes and JSON escaping can inflate control or invalid bytes to about six bytes per character. `remote_addr`, `method`, `route`, `status`, `bytes` and `duration_ms` are unchanged. Proven over a socket too: with `CALC_SHUTDOWN_DRAIN=4s` and SIGTERM, ten draining `/readyz` 503 access lines are all `INFO` and the whole log has zero `ERROR` lines (`evidence/sigterm-live.txt`).
- (b) **OBS** [topic: observability, security-privacy] [type: debt] [resolved: OBS-LOG-02] — `method` is logged raw and is bounded only by the HTTP token grammar and the 16 KiB header limit, so a client can still write a method of up to about 16 KiB into every access line (owner decision U20 bounds `path` and `user_agent` and keeps every other field unchanged). Options for the owner: truncate it the same way (256 characters), or log `OTHER` for a method outside the standard set as the metrics label already does. Decided at the M2 transition (2026-10-22, U30): `method` is truncated to 256 characters in OBS-LOG-02 (RUN-M2-0).
- (c) **OBS** [topic: observability] [type: note] — `SetAccessLevel` can lower any 5xx: the handler that answers owns the level of its line (U19). The only fallback that could turn a readiness response into a 500 after the level is set is `WriteJSON`'s marshal-failure path for a struct of three strings (`respond.go`, documented unreachable); no check ties the level to the status the handler intended. Reviewed and accepted.

### Findings of OBS-LOG-02 — Bounded method in the access log (2026-10-22)
- (a) **OBS** [topic: observability, security-privacy] [type: rule] — Rule as built: `logAccess` (`backend/internal/platform/httpx/middleware.go`) writes `method`, `path` and `user_agent` through `truncateChars(…, maxLoggedChars)` (256 characters, rune-aware, never splitting a UTF-8 sequence); `remote_addr` and every other field are unchanged. `TestAccessLogBoundsMethod` pins 300 → 256, `GET` unchanged, 256 unchanged, 257 → 256 and that status, route and level are untouched; removing the truncation fails two cases. Live proof (built binary, raw socket request with a 300-character method): the access line carried a 256-character `method`, the response was the 405 problem (`evidence/obs-log-02.txt`).
- (b) **OBS, API** [topic: security-privacy, observability] [type: debt] [resolved: OBS-LOG-02] — The 405 problem `detail` still reflects the whole request method (`backend/internal/httpapi/methods.go:24-26`), and RNF-SEC-02 justifies that as «bounded by the HTTP token grammar», but the real bound is the 16 KiB header limit (`internal/app/app.go:90`): the live check of OBS-LOG-02 got a 405 body that echoed all 300 characters. U30 names only the access log, so this run left it unchanged. Options for the owner: cut the method in the detail to 256 characters like the log (and amend the RNF-SEC-02 sentence), or keep the behaviour and correct the sentence to «bounded by the 16 KiB header limit». Found by the spec review of RUN-M2-0.
