# Findings — API (HTTP API and contract)

### Findings of API-CONTRACT-01 — OpenAPI contract and Redocly configuration (2026-10-22)
- (a) **API** [topic: api-contract, testing-environment] [type: debt] [resolved: API-ROUTES-01] — Response validation against the document looks operations up by the request's method, so a wrong-method request (no operation for that method) cannot be validated as a response of the contract (`POST Path '/healthz' not found`, libopenapi-validator v0.16.1). The contract tests validate every 405 body against `#/components/schemas/Problem` and assert the `Allow` header instead, for the operation endpoints and for `/healthz`, `/readyz` and `/api/v1/openapi.yaml`.
- (b) **UI, OPS** [topic: api-contract] [type: debt] [resolved: OPS-EDGE-01] — `Problem.required` in the contract is `type, title, status, detail, code, requestId` (RF-API-05/07: every problem carries them; `instance` may be omitted only by the edge). Consequences: the generated `Problem` type has `detail` and `requestId` as required strings, so the client's `isProblem` guard checks both are strings and the problem result copies them without `!== undefined` conditions (strict lint flags unnecessary conditions; RF-UI-09's `detail?`/`requestId?` stay optional in the client's own result type); the edge's 429/503/413 problems built in nginx carry `detail` and the validated `requestId` and validate against the schema. The service side is enforced by the contract tests of API-ROUTES-01, which validate every problem response against the document.
- (c) **OPS** [topic: testing-environment, ci-supply-chain] [type: trap] — `pnpm dlx @redocly/cli@<version> lint` fails with `ERR_PNPM_DLX_MULTIPLE_BINS` (the package ships `redocly` and `openapi` binaries). Working form: `pnpm --package=@redocly/cli@<version> dlx redocly lint backend/api/openapi.yaml`. Measured: about 2 s per lint with Redocly CLI 2.69.0.
- (d) **API** [topic: api-contract] [type: rule] — Rule as built: each operation of `backend/api/openapi.yaml` declares the statuses the requirements assign to it: `listOperations` 200/405/429/500/503; `calculate` 200/400/404/405/413/415/422/429/500/503; `getOpenAPIDocument` 200/405/429/500/503; `getLiveness` 200/405/500; `getReadiness` 200/405/500/503 (Health). 405 on every GET-only path (RF-API-06), 500 everywhere (RF-API-11), edge 429/503 only on `/api/*` (RF-OPS-04; probes pass through). Status keys ascend; `operation-4xx-response` stays an error.

### Findings of API-HTTPX-01 — HTTP platform: problems, decoding, request context, middleware (2026-10-22)
- (a) **API** [topic: api-contract, security-privacy] [type: rule] — Rule as built: `httpx.DecodeJSON` checks the media type (415), reads the whole body through `http.MaxBytesReader` (413 for any body over 4096 bytes, whatever its content), then parses: empty → `request body must not be empty`; syntax → `request body is not valid JSON`; trailing data, a non-object top level (including `null`) or a wrong JSON type → `request body must contain a single JSON object`; top-level keys must be byte-equal to the destination struct's JSON names and nested unknown names are rejected by the strict decoder → `unknown field "<name>"` (`%q`). No other MALFORMED detail exists and no type-mismatch detail names a field. Repeated keys: the last occurrence wins; the same key in another case is an unknown field.
- (b) **API** [topic: api-contract, testing-environment] [type: trap] — `encoding/json` (Go 1.27.3) matches object keys case-insensitively (`{"OPERANDS":["9"]}` fills `operands` even with `DisallowUnknownFields`), decodes `null` into a struct pointer without error, puts map keys from the input into `UnmarshalTypeError.Field`, and reports unknown fields only as the untyped text `json: unknown field "<name>"`. A streaming decoder over `MaxBytesReader` reports a syntax error in an oversize body before the size error.
- (c) **API** [topic: api-contract] [type: note] — `httpx.Codes()` returns the 11 codes the service emits; the contract's `ProblemCode` enum has 13 (`RATE_LIMITED` and `SERVICE_UNAVAILABLE` are edge-only, RF-API-05). The integration check is `Codes()` ⊆ contract enum = the client's `PROBLEM_CODES`, as RF-API-09 states.
- (d) **API** [topic: api-contract] [type: debt] [resolved: API-ROUTES-01] — Consumer interface as built: `httpx.WriteJSON(w, r, status, v)` takes the request (its encoding fallback is a complete problem with `instance` and `requestId`); a `[]` body yields `request body must contain a single JSON object` (RF-API-04 rule 4); `DecodeJSON` into `struct{ Operands json.RawMessage \`json:"operands"\` }` enforces the exact `operands` key. API-ROUTES-01's router table uses these texts and calls.
- (e) **OBS** [topic: observability, reliability-errors] [type: debt] [resolved: OBS-METRICS-01] — The metrics middleware sits between AccessLog and Recover (RF-API-12): it must read the status from `httpx.Info(ctx).StatusOrOK()` in a `defer` (as AccessLog does), because when a panic happens after the response started Recover sets the recorded status to 500 and re-panics `http.ErrAbortHandler`; a middleware that records after `next` returns, or from its own writer wrapper, would miss that request or count it with the status already sent.
- (f) **OBS** [topic: observability, live-verification] [type: verification] [resolved: OBS-RUNTIME-01] — RF-API-11/12 «a panic is logged with its request ID and counted as a 500» is proved in httpx with a test handler that adds `request_id` from the context; the real chain (request-aware logger of OBS-METRICS-01, the metrics middleware, the composed handler of OBS-RUNTIME-01) needs one end-to-end test: a panicking route returns the 500 problem, the panic line carries the same `request_id` as the header, the access line and `http_requests_total` record 500.
- (g) **API** [topic: security-privacy, observability] [type: note] — Decisions as built after the security review: Recover aborts a response that has already started (`http.ErrAbortHandler` after recording 500) instead of leaving a complete-looking truncated body. Not changed, by decision: the 405 detail echoes the request method in full — net/http limits it to the token grammar and the header limit (16 KiB from OBS-RUNTIME-01), it is JSON-encoded and served `nosniff`, and RF-API-06 fixes the detail format; a client that disconnects mid-body is answered (and logged) as a 400 `request body is not valid JSON`; a handler that aborts with `http.ErrAbortHandler` before writing is logged with status 200.

### Findings of API-ROUTES-01 — Routes, handlers and contract tests (2026-10-22)
- (a) **API** [topic: api-contract, security-privacy] [type: rule] — Rule as built (`backend/internal/httpapi`): `NewRouter` sets `Cache-Control: no-store` on every response, answers a target that is not a canonical absolute path (`*`, empty, `//`, `.`/`..` segments, checked on `EscapedPath()` so `%2e` and `a%2Fb` stay single segments) with the NOT_FOUND problem instead of a mux redirect or empty 400, and registers `/api` exactly; every pattern is tagged with `httpx.Route`; calculate checks the catalog snapshot before touching the body (zero reads asserted), then `httpx.DecodeJSON` into `{operands json.RawMessage}`, then `operands` absent/`null` → `is required`, anything but an array whose every element is a JSON string (`[null]`, `["1",null]`, a string, an object, numbers) → the wrong-type reason, then arity and operand errors from `calc`; a cancelled request context → 500 INTERNAL_ERROR logged at WARN `calculation canceled`, any other unexpected error → 500 logged at ERROR, never in the body; every JSON response goes through `httpx.WriteJSON(w, r, …)`; the contract is served byte-identical with `application/yaml`, `no-store` and `Content-Length`. Contract tests validate every documented service status with `ValidateHttpResponse`, the 405 and unmatched-404 bodies against `#/components/schemas/Problem` with `Allow` asserted, the list order against the catalog, `OperationName` order and `httpx.Codes()` ⊆ `ProblemCode` with the two edge-only codes absent.
- (b) **API** [topic: security-privacy, api-contract] [type: debt] [target: API-backlog] — `instance` reflects the decoded request path in every problem (`httpx.WriteProblem`, `respond.go:25`), as RF-API-05 requires («instance = request path»), but RNF-SEC-02 lists only three reflected inputs (operation name, unknown field, 405 method). The value is JSON-escaped and served with `nosniff` and `default-src 'none'`, so it is not an injection, but a path up to the 16 KiB header limit is echoed (twice for UNKNOWN_OPERATION: a 15 KB path produced a 30 KB response). Options for the owner: add the path in `instance` to the RNF-SEC-02 exceptions, or cap the reflected path length in `httpx` with a contract-compatible `instance`.
- (c) **API** [topic: reliability-errors, observability] [type: note] — A request whose context is already cancelled (UC-API-02 E14) is answered 500 INTERNAL_ERROR (the contract has no other status for it) and counted `outcome="canceled"`; the handler logs it at WARN, but the access log (5xx → ERROR, RF-OBS-05) and `http_requests_total{status="500"}` still record a 500. Accepted at spec review.
- (d) **API** [topic: api-contract, observability] [type: note] — Responses that net/http writes itself never reach the handler chain: 431 for headers beyond `MaxHeaderBytes` plus its 4 KiB slack, 400 for invalid header values or request lines, and the `OPTIONS *` reply. They are plain text without `X-Request-ID`, not logged and not counted; they carry fixed text only.
- (e) **DOC** [topic: performance-scale] [type: debt] [target: DOC-README-01] — U12 is implemented: `BenchmarkCalculateWorstCase` (seven range-edge fractional powers) measured 4.7–19.5 ms/op (max of three runs, `heavy` lease, alone) against its 50,000,000 ns/op budget, and the six `BenchmarkCalculate` cases 1.8–502 µs/op against 1,000,000 ns/op (`power_fractional` 502 µs, margin still under 2×; evidence/bench.txt). The README benchmark table and `docs/verification.md` must publish both benchmarks with both budgets.
